# Additional account-menu context qualification

The `karum-single` signed marketplace profile retains its original financial
predicates and its two original zero-balance menu opens and closes. Additional
observations use the existing seller and positively funded buyer fixture
accounts. They do not mint funds, submit a transaction, replace product APIs or
RPC replies, or change the selected frontend, Core, navigation or CI deadlines.

An independent Node client reads both balances at one canonical block hash. With
the menu open, the existing fixture provider emits `accountsChanged`. The real
wallet handler, Vue watcher, original public client and Node RPC must show the
newly selected account's exact independently formatted amount. The observer
holds one original request for the prior account before transport, continues it
once without changing its payload, and checks its matched HTTP/JSON-RPC reply.
After that reply, the prior zero amount must not replace the new positive amount;
the converse positive-to-zero case must also pass. Both closes clear the amount,
the original seller context is restored, and the canonical head is unchanged.

The added `ACTUAL-ACCOUNT-MENU-CONTEXT` record is separate from the original
52-profile/1244-check financial matrix. In-memory controls qualify the observer's
selection and refusal logic; they are not browser execution. Exact-source hosted
CI must establish the production-page observations. These isolated public test
accounts do not qualify physical wallets, public networks, independent NoM
canonicality, production funds, release or deployment.

The additional observer runs after the original `bind` phase has joined the
existing funding prefix and before the admitted-item projections and purchase.
The initial listing page is at height six; the bind operation executes the later
funding messages. No new funding messages are introduced. The observer accepts
the SDK's one-entry JSON-RPC batch, continues the same request once, and requires
one matching reply with the original ID and independently expected amount.
Multiple-entry requests and mismatched, error or differently shaped replies are
refused by the observer. The original 45 controls remain; eight additional
controls cover the SDK batch boundary and strict reply selection.
